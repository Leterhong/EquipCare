## 0. 框架定位

EquipCare 不只是"一个能跑的巡检维保系统"，而是一套**设备域业务框架**——你自带业务需求进来，
横切设施全部现成：

| 你不用再写的 | 框架已提供 |
|---|---|
| 认证/授权 | JWT 双令牌 + Spring Security + 权限码模型（`@PreAuthorize`） |
| 操作审计 | `@AuditLog` 注解 + AOP 切面（脱敏/traceId/异步落库） |
| 状态可追溯 | 只插入状态轨迹表模式（`wo_status_log` 同款） |
| 事件广播 | `DomainEventPublisher` → 事务性 Outbox → 站内消息 + SSE 实时推送 |
| 通知外发 | 企业微信 webhook / SMTP 邮件（配置即用） |
| 统一响应/异常/分页 | `Result` / `GlobalExceptionHandler` / `PageQuery` |
| 前端骨架 | 原生 ES Module 前端（28 页）+ Vue3 新前端工程，双端共存 |
| 架构守护 | ArchUnit 测试自动拦截违规依赖 |

空库启动：`schema.sql`（37 表）+ `seed.sql`（仅角色/权限/字典/SLA 默认政策），
引导参数创建首个管理员，业务数据由实际使用产生——**仓库里没有任何演示数据**。

## 1. 新增业务模块 · 七步法

以新增「保养管理（maintenance）」为例，全部改动集中在
`equipcare-business/src/main/java/com/equipcare/maintenance/`：

**① 建包**（沿用既有六层结构）

```
com.equipcare.maintenance/
├── controller/  MaintenanceController
├── dto/         PlanSaveDTO, PlanQuery …
├── entity/      MtPlan, MtRecord …
├── enums/       PlanStatus …
├── mapper/      MtPlanMapper …          ← @MapperScan("com.equipcare.**.mapper") 自动覆盖
├── service/impl MaintenanceService …
├── vo/          PlanVO …
└── event/       MaintenanceDueEvent …   ← 需要广播才建
```

**② 实体**：继承 `com.equipcare.common.domain.BaseEntity`（自动填充
createTime/updateTime/createBy/updateBy + 逻辑删除），表加进 `database/schema.sql`。

**③ Service**：注入其他域用**对方的 Service 接口**（同 jar 内直接注入；跨 Maven 模块
遵守依赖方向，见 §2）。状态类字段变更**只走 CAS 更新**并写轨迹表（仿 `wo_work_order`）。

**④ Controller**：每个端点挂权限码与审计：

```java
@PreAuthorize("hasAuthority('maintenance:plan:dispatch')")
@AuditLog(module = "保养管理", action = "派发保养单")
```

权限码写入 `seed.sql` 的 sys_permission 段（或运行期在「权限管理」页配置）并分配给角色。

**⑤ 领域事件**（需要通知/实时刷新时）：
`event/` 下建 record → 业务事务内 `domainEventPublisher.publish(new MaintenanceDueEvent(...))`
→ 在 `notification/listener/DomainEventNotificationListener` 加一个 instanceof 分支
（站内消息 / `sseHub.sendToAll` / 外发通知任选）。Outbox 保证与业务同生共死。

**⑥ 前端**：旧前端 `static/js/pages/maintenance-*.js` + `app.js` 路由
（perm 与后端一致，菜单自动按权限显示）；或迁入 Vue 端（见 `equipcare-web/README.md` 迁移约定）。

**⑦ 测试**：纯逻辑写单测（放对应模块 `src/test`）；端到端写 Python 冒烟脚本
（仿 `scripts/stage3-smoke.py`）。`mvn test` 中 ArchUnit 会自动校验新模块的依赖方向。

## 2. 架构红线（ArchUnit 已固化，CI 强制）

```
common ← system ← framework          ← admin
common ← system ← business/ai    ────┘
```

- `common` 禁止依赖任何上层；
- 业务模块禁止依赖 `framework`（横切能力经 common 接口反转：登录上下文、
  领域事件发布、SseHub、审计注解全部在 common）；
- `OutboxEventArrived` 信封只允许 `notification` 模块消费；
- 状态字段禁止绕过 CAS 更新（全库唯一写状态列的 SQL 必须带版本条件）。

## 3. 事件接入点速查

| 已有事件 | 发布模块 | 下游动作 |
|---|---|---|
| WorkOrderCreated / StatusChanged | workorder | SSE 看板刷新 |
| SlaAlertTriggered | workorder | 站内消息 + SSE + 企微/邮件 |
| StockLow | inventory | 站内消息 + SSE + 企微/邮件 |
| InspectionAnomalyFound | inspection | SSE 广播 |

新增事件零成本：发 record 即得「消息 + SSE + 外发」三通道，无需自己对接任何推送设施。

## 4. 配置扩展点（全部可选、默认关闭）

| 配置 | 用途 |
|---|---|
| `equipcare.ai.*` | AI Provider（OpenAI 兼容）+ 视觉/嵌入模型 + 知识库开关 |
| `equipcare.notify.wecom/webhook-url`、`equipcare.notify.mail.*` | 外发通道 |
| `equipcare.outbox.dispatch-interval-ms` | 事件投递节奏 |
| `equipcare.*.scheduler.*` | 各调度器独立开关与间隔 |

## 5. 目录速查

| 想改什么 | 去哪里 |
|---|---|
| 统一响应/异常/错误码 | `equipcare-common/.../result`、`exception` |
| 登录态/令牌 | `common/security`（接口层）+ `framework/security`（安全链） |
| 事件投递策略 | `framework/outbox` |
| SSE 通道 | `common/realtime/SseHub` + `framework/realtime/SseController` |
| 通知渠道 | `business/notification/outbound` |
| 数据库结构 | `database/schema.sql` + 幂等增量脚本 |
