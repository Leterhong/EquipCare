## 一页看懂核心设计

### 主干业务链路

```
设备建档 → 巡检模板 → 巡检计划 → 巡检任务 → 现场执行
   → 异常记录 → 自动转工单 → 派单 → 接单 → 维修（领备件）
   → 提交验收 → 验收通过/驳回 → 设备复用 → 健康分与数据分析
```

### 工单状态机（7 态 12 动作）

```
PENDING_DISPATCH ──派单──> PENDING_ACCEPT ──接单──> IN_PROGRESS ──提交──> PENDING_VERIFY ──通过──> COMPLETED
       │                        │  ↑                    │  ↑                    │
       │                     拒接/撤回                挂起↓ 恢复              驳回
       │                        ↓                    SUSPENDED ────────────────┘
       └──────取消────> CANCELLED
```

### 六个关键设计决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 架构形态 | 模块化单体，单 Maven 模块 + 包级隔离 | 单人开发，本地事务即可保证"任务+异常+工单"强一致，微服务的分布式事务与运维成本无法承担 |
| 状态管理 | 状态机唯一入口 + 转移表 + 条件更新 + 全量状态日志 | 从代码结构上杜绝"随手改状态"，84 种状态×动作组合单测全覆盖 |
| 异常转单 | 事务内同步建单 + `anomaly_id` 唯一索引 + 同设备同类工单合并 | 保证不丢单、不重单、不产生工单风暴 |
| SLA | 业务状态与考核状态双轨，超时只升级告警不改状态 | 避免超时导致工单"消失"、设备未修好却闭环 |
| 健康分 | 可拆解的 5 项扣分公式 + 每日快照 | 评审可当场追问"为什么扣 23 分"，答案在快照表里 |
| AI 依赖 | 无任何 AI Key 时功能 100% 可用 | 满足任务要求第 10 条，避免演示环境不可控 |
