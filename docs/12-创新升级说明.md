## 1. 升级总览

本期在不破坏既有 28 个业务页面、零业务逻辑变更的前提下完成四条创新线：

| 创新线 | 交付物 | 关键词 |
|---|---|---|
| 架构层 | 领域事件 + 事务性 Outbox + 架构守护测试 | `event_outbox`、`DomainEventPublisher`、ArchUnit |
| 实时层 | SSE 推送中心（票据鉴权 + 心跳 + 生命周期管理） | `/api/sse/*`、`SseHub`、EventSource |
| AI 层 | 新 Maven 模块 `equipcare-ai`：故障诊断（流式）/ 智能派单 / 维修报告 | OpenAI 兼容多 Provider、fail-open |
| 前端层 | AI 副驾面板、实时铃铛、暗色模式、摄像头扫码、PWA | 原生 JS 增量，28 页全兼容 |

技术选型说明：事件驱动采用「原生 Spring 事件 + 自研轻量 Outbox + ArchUnit 守护」
而非 Spring Modulith——Modulith 的持久化事件注册表需要 JPA/Hibernate 与现有
MyBatis 栈共存，且其严格 verify() 会被已知的 workorder↔inventory 环依赖卡死
（该环已文档化为技术债）。三个交付物（事件/Outbox/边界验证）全部落地为可控代码。

方案经跨模型评审（豆包 seed 架构师视角）修正五处风险设计：
Outbox 原子认领（PROCESSING+锁+超时回收）、SSE 按用户注册表+单用户连接上限+
最大生命周期、票据一次性原子消费、AI 流式中断清理+受控降级、前端指数退避重连。

## 2. 架构层：领域事件与事务性 Outbox

### 2.1 数据流

```
业务事务（如工单状态流转）
   ├─ 业务表变更（casUpdateStatus / wo_status_log …）
   └─ DomainEventPublisher.publish(event)         ← 同一事务内
        └─ INSERT event_outbox(PENDING)            ← 与业务同事务提交
             ↓ afterCommit（快速路径）
        OutboxDispatcher.dispatchById(id)           ← 原子认领 PROCESSING
             ↓ 反序列化 → publishEvent(OutboxEventArrived)
        DomainEventNotificationListener（notification 模块唯一信封消费者）
             ├─ 站内消息 MessageService.send        （SLA/库存事件）
             └─ SseHub 实时推送                     （全部事件）
             ↓
        markSuccess / 失败退避重试(5s→10min) / 8 次判 DEAD
```

- **一致性**：业务回滚 ⇒ 事件消失；业务提交 ⇒ 事件必达（至少一次）。
- **崩溃恢复**：快速路径失败或进程崩溃后，调度器每 10 秒补投 PENDING；
  PROCESSING 超 120 秒视为 Worker 崩溃自动回收。
- **幂等要求**：监听方需容忍重复——SLA 去重由 `sla_alert_record` 唯一键、
  库存去重由消息表当天计数兜底（与升级前行为一致）。

### 2.2 已定义的领域事件

| 事件 | 模块 | 触发点 | 下游 |
|---|---|---|---|
| `WorkOrderCreatedEvent` | workorder | 人工/扫码/巡检转单建单 | SSE `workorder:changed` |
| `WorkOrderStatusChangedEvent` | workorder | 七态状态机每次 CAS 流转 | SSE `workorder:changed` |
| `SlaAlertTriggeredEvent` | workorder | SLA 扫描当日首次超时 | 站内消息 + SSE `sla:alert` |
| `StockLowEvent` | inventory | 库存扫描当日首次低于安全线 | 站内消息 + SSE `stock:low` |
| `InspectionAnomalyFoundEvent` | inspection | 巡检提交发现异常项 | SSE `anomaly:found` |

新增事件三步：业务模块 `event/` 包下建 record → 发布点调
`domainEventPublisher.publish(...)` → 在 notification 桥接监听器加一个分支。

### 2.3 架构守护测试

`equipcare-admin/src/test/java/com/equipcare/ArchitectureRulesTest.java`（ArchUnit）：
业务模块禁止依赖 framework/security/outbox/realtime 包；common 禁止反向依赖任何
上层；OutboxEventArrived 信封只允许 notification 消费。`mvn test` 即验证。

## 3. 实时层：SSE 推送中心

### 3.1 端点与鉴权

- `POST /api/sse/ticket`（JWT 保护）：签发 30 秒一次性票据（SecureRandom 256 位，
  每用户每分钟限 10 张）；
- `GET /api/sse/stream?ticket=`（白名单放行）：票据即凭证，一次性原子消费，
  身份由票据携带（EventSource 无法携带 Authorization 头的业界标准解法）。

### 3.2 事件清单（前端监听名）

| 事件名 | 定向 | 载荷 |
|---|---|---|
| `connected` | 单连接 | 握手 + 在线数 |
| `message:new` | 收件人 | `{id,title,msgType,bizType,bizId}` |
| `workorder:changed` | 全员 | 工单创建/状态流转事件原文 |
| `sla:alert` | 收件人 | `{workOrderId,orderNo,stage,overdueMinutes}` |
| `stock:low` | 全员 | `{partId,partName,currentStock,safetyStock}` |
| `anomaly:found` | 全员 | 巡检异常事件原文 |

每条业务事件带 `id`（outbox 主键），客户端按 lastEventId 去重。

### 3.3 资源治理（评审修正点）

- 注册表按用户分桶（`ConcurrentHashMap<Long, Set<Emitter>>`），单用户最多 3 连接（淘汰最旧）；
- onCompletion/onTimeout/onError 三钩子摘除，推送失败立即摘除；
- 心跳 20 秒注释帧 `: ping`（不进业务消息流）；
- 单连接最大生命周期 30 分钟，服务端主动断开促重连；
- Nginx：`/api/sse/` 独立 location，`proxy_buffering off`、读超时 35 分钟
  （见 `deploy/nginx.conf`）。

### 3.4 前端接入

`static/js/realtime.js` 单例通道：票据 → EventSource → 指数退避重连
（1s·2ⁿ + 抖动，封顶 30s，6 次后放弃）→ 失败自动回退 30 秒轮询；
业务页面零侵入订阅：

```js
window.addEventListener('ec:sse', (e) => { /* e.detail = {type, data} */ });
window.addEventListener('ec:sse-refresh', ...);  // 需要刷新数据的页面
```

铃铛策略：实时在线 5 分钟对账一次，断线回 30 秒轮询。

## 4. AI 层：equipcare-ai 模块

### 4.1 配置（OpenAI 兼容，多 Provider）

```yaml
equipcare:
  ai:
    enabled: ${EQUIPCARE_AI_ENABLED:false}     # 默认关；不配 Key 系统功能不受影响
    base-url: ${EQUIPCARE_AI_BASE_URL:https://ark.cn-beijing.volces.com/api/v3}
    api-key:  ${EQUIPCARE_AI_API_KEY:}
    model:    ${EQUIPCARE_AI_MODEL:}           # 如 doubao-seed-1-6-251015 / glm-4.7 / deepseek-chat
    max-concurrent-streams: 4                  # 全局流式并发上限（另有单用户互斥）
```

红线：`enabled=false` 时 `/api/ai/diagnosis|dispatch-suggest|report` 整体不装载
（404），前端经 `/api/ai/status` 探测后自动隐藏 AI 入口——**不依赖付费 AI 也能跑**。

### 4.2 三个能力

| 端点 | 权限 | 输入数据（全部来自既有库） | 输出 |
|---|---|---|---|
| `GET /api/ai/diagnosis/{id}/stream` | 登录即可 | 工单+设备档案+健康分+状态轨迹+维修记录+领用备件+同设备历史 5 单 | SSE 流式 Markdown：根因分析/维修步骤/备件工具/安全注意 |
| `POST /api/ai/dispatch-suggest/{id}` | `wo:workorder:dispatch` | 候选维修工（同类别修复数/累计修复/在办负荷，算法预打分） | TOP3 推荐 JSON（模型失败自动降级纯算法 TOP1） |
| `POST /api/ai/report/{id}` | `wo:workorder:view` | 工单全生命周期：时间线/维修记录/备件成本/评价 | Markdown 报告（可复制/下载 .md） |

可靠性设计：JDK HttpClient 直连（零新依赖）、连接 5s/请求 180s 双超时、
前端断开即取消上游（停烧 token）、单用户互斥 + 全局信号量、非 2xx 不进流解析、
流内受控降级（`ai.error` 事件带明确错误码，不伪装成功）、全部挂 @AuditLog 审计。

### 4.3 使用步骤（演示路径）

1. `.env`（或环境变量）设置 `EQUIPCARE_AI_ENABLED=true` + `EQUIPCARE_AI_API_KEY` + `EQUIPCARE_AI_MODEL`；
2. 重启后端，登录 PC 端 → 任意工单详情页可见「AI 智能副驾」卡片；
3. 点「⚡ AI 故障诊断」观看流式输出；派单弹窗点「⚡ AI 推荐维修人」；工单页「📄 生成维修报告」。
