## 1. 三个候选模型

| 模型 | 隔离方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| A. 行级共享 | 全表加 `tenant_id` + MyBatis-Plus `TenantLineHandler` 自动注入 | 成本最低、跨租户运营报表天然支持、单库运维 | 隔离靠代码纪律（拦截器遗漏即泄露）、大租户噪声影响邻居、备份只能整体 | 中小 SaaS 起步（**推荐**） |
| B. Schema 级 | 每租户一个 MySQL schema，同实例 | 隔离清晰、可按租户备份/恢复 | 连接池路由复杂、跨租户统计要 UNION、schema 数量上限 | 租户数 < 500、合规中等 |
| C. 库级 | 每租户独立数据库/实例 | 最强隔离与合规（等保/私有化友好） | 成本最高、运营/升级最贵（N 份 schema 漂移管理） | 大客户/私有化交付 |

**决策建议**：A 起步 + 为 C 预留（租户维度数据天然可整体导出迁库）。
理由：目标客群是中小工厂设备科，起步租户数少；框架的 MyBatis-Plus 栈对
`TenantLineHandler` 支持是一等公民（行级注入对业务代码零侵入）。

## 2. 模型 A 落地设计（行级隔离）

### 2.1 数据层

1. 所有业务表（eq_/insp_/wo_/sp_/sla_/event_outbox/ai_kb_document…）加
   `tenant_id BIGINT NOT NULL DEFAULT 0`（0 = 系统预置/单租户模式），
   **索引全部改为 (tenant_id, …) 联合前缀**；
2. `sys_user/sys_role/sys_dept/sys_permission/sys_dict` 特殊处理：
   - 权限码、数据字典：**全局共享**（不隔离），角色/用户/部门按租户隔离；
   - `sys_role-permission` 分配关系按租户（各租户可自行裁剪权限）；
3. `sys_file`/上传目录：`upload/{tenantId}/2026/11/07/…`（现有 dayPath 前插租户段）。

### 2.2 拦截层（对业务代码零改动）

MyBatis-Plus `TenantLineHandler`：

```java
public class EquipCareTenantLineHandler implements TenantLineHandler {
    public Expression getTenantId() {
        Long tid = TenantContext.get();                 // 登录人所属租户
        return new LongValue(tid == null ? 0L : tid);
    }
    public String getTenantIdColumn() { return "tenant_id"; }
    public boolean ignoreTable(String table) {
        return SHARED_TABLES.contains(table);           // sys_permission/sys_dict…
    }
}
```

- **写入**：INSERT 自动补 tenant_id；UPDATE/DELETE 自动追加 WHERE（防跨租户篡改）；
- **读取**：SELECT 自动追加 WHERE；
- **例外通道**：outbox 调度器/定时任务/引导程序等无登录上下文场景用
  `TenantContext.runAs(0L, () -> …)` 显式跨租户；
- **风险点（必须写测试）**：原生 SQL 的自定义查询（如 ExportMapper 的跨表报表）
  不会被 TenantLineHandler 覆盖——报表 SQL 需手工带 tenant_id 或改走 Wrapper。

### 2.3 上下文与认证

- `sys_tenant` 新表（租户开通/套餐/状态）；`sys_user.tenant_id`；
- JWT claims 增加 `tid`；`LoginUser` 带 tenantId；`TenantContext`（ThreadLocal，
  参照 `SecurityUtils` 模式）；
- Redis 键全部加租户前缀：`loginFail:{tid}:{username}`、SSE 票据、TokenStore 会话
  （Key 结构变更 → 迁移期双读）；
- 登录入口按租户路由：子域名（`{tenant}.equip.example.com`）或登录页选租户/邮箱后缀。

### 2.4 应用层

- 管理端新增「租户管理」（开通/停用/配额）；bootstrap 引导改为「首租户管理员」；
- 配额：设备数/存储量/月 AI token 上限（`sys_tenant.quota` JSON），
  超限在服务入口统一拒绝；
- 前端无感（token 内已含租户身份）。

## 4. 风险清单

1. **泄露风险集中在自定义 SQL**：框架的 Wrapper 查询全部自动覆盖，
   原生 @Select/注解 SQL 是唯一漏点——引入规则：新增原生 SQL 必须在
   ArchitectureRulesTest 之外的专项清单登记；
2. **event_outbox 跨租户**：事件消费侧（通知/外发）必须以租户上下文执行，
   否则 A 租户的 SLA 预警会发到 B 租户的群机器人（webhook 也应租户化配置）；
3. **索引膨胀**：联合前缀会放大索引体积，大表（审计日志/消息）建议按月分区；
4. **AI 知识库**：`ai_kb_document` 必须隔离（各租户知识独立），RAG 检索
   先按 tenant_id 过滤再算余弦。

## 5. 实施顺序建议

1. 先做「租户感知」基础设施（tenant_id 列 + 拦截器 + TenantContext + 专项测试），
   单租户模式运行（所有数据 tenant_id=0）——**零功能变化**；
2. 上 sys_tenant 表 + 登录路由 + 配额；
3. 最后开放多租户注册入口。

> 该顺序的关键好处：第 1 步完成后，代码已具备多租户形态但对外仍是单租户产品，
> 风险被完全摊平；任何一步都可独立回滚。
