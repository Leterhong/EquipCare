## 1. 项目定位与目标

### 1.1 业务痛点

设备管理现场普遍存在四类断点：

1. **档案断点**：设备台账在 Excel 里，现场无标识，巡检人员靠记忆找设备。
2. **执行断点**：巡检靠纸单，漏检、代签、事后补单无法识别，异常发现依赖人的责任心。
3. **流转断点**：巡检发现异常后走微信群口头报修，谁派单、谁在修、修到哪一步无据可查。
4. **核算断点**：维修换了多少备件、备件库存是否准确、单台设备年度维修成本多少，全部无法回答。

### 1.2 产品目标

用一套系统把「设备 → 巡检 → 异常 → 工单 → 派单 → 维修 → 备件 → 验收 → 数据」串成一条可追溯、可度量、可考核的闭环。

| 目标 | 可量化指标 |
|---|---|
| 巡检执行可验证 | 巡检任务扫码进入率 100%，漏检率可统计（任务逾期数/应执行数） |
| 异常转单零丢失 | 高等级异常 100% 自动生成工单，异常-工单关联率 100% |
| 维修过程可追溯 | 每张工单至少 1 条维修记录 + 1 条状态流转日志，全链路时间戳齐全 |
| 备件账实一致 | 库存流水 before/after 快照连续，任何时点可反推库存 |
| SLA 可考核 | 响应超时、修复超时分别统计，达成率按角色/班组出报表 |
| 设备状态可预警 | 每台设备每日健康分，低于 60 分自动进入高危清单 |

### 1.3 非目标（明确不做，控制独立开发复杂度）

| 不做的事 | 原因 |
|---|---|
| 微服务拆分、服务注册中心、消息中间件 | 单人开发，单体 + 模块化包结构已满足，运维成本不可接受 |
| 多租户 SaaS 隔离 | 赛事场景为单企业部署，多租户会显著放大权限与数据模型复杂度 |
| 原生 App / 小程序 | H5 移动端页面已满足扫码巡检，避免双端维护 |
| 可视化拖拽流程引擎 | 工单状态机为固定 8 态，用代码枚举 + 转移表实现更可控、可测试 |
| 对接企业微信/钉钉审批 | 依赖外部资质，站内消息 + 待办已闭环 |
| 付费 AI 模型强依赖 | 任务要求第 10 条，系统在无任何 AI Key 的情况下必须完整可用 |

## 2. 用户角色定义

| 编码 | 角色 | 典型人员 | 核心诉求 | 数据范围 |
|---|---|---|---|---|
| `ADMIN` | 系统管理员 | IT 运维 | 账号、角色、权限、字典、审计，系统可用 | 全量 |
| `EQUIP_ADMIN` | 设备管理员 | 设备科/后勤主管 | 台账、模板、计划、派单、备件、SLA 配置 | 全量（可配置为部门） |
| `INSPECTOR` | 巡检人员 | 班组巡检员 | 领任务、扫码巡检、上报异常 | 仅本人任务与本人上报异常 |
| `REPAIRMAN` | 维修人员 | 维修工/外协 | 接单、记录维修过程、领用备件、提交验收 | 仅派给自己的工单 |
| `VERIFIER` | 验收人员 | 设备管理员兼任或独立质检 | 验收通过/驳回、质量评分 | 待验收工单 + 历史验收记录 |
| `MANAGER` | 企业负责人 | 厂长/校长/园区负责人 | 看板、报表、SLA 达成、成本 | 全量只读，无写权限 |

**角色互斥硬约束**（写入后端校验，不可通过配置绕开）：

- 工单的**维修人不得是本人验收人**，`verify_user_id != assignee_id`，否则接口返回 `WO_SELF_VERIFY_FORBIDDEN`。
- 巡检任务的**执行人不得是计划创建人兼任审核人**的场景本系统不涉及审批，仅约束任务执行人必须是任务 assignee。
- `MANAGER` 角色对所有写接口一律 403，仅开放查询与导出。

## 3. 功能需求清单

编号规则：`FR-xx` 对应任务书 17 项功能。每条包含「角色 / 主流程 / 业务规则 / 异常分支」，规则即为后续验收与单测依据。

### FR-01 设备资产管理

- **角色**：EQUIP_ADMIN 增删改；全角色按权限查询
- **主流程**：新增设备 → 系统生成资产编号与二维码 token → 绑定类别/位置/责任人 → 台账列表可查 → 二维码打印贴机
- **业务规则**
  1. `asset_no` 全库唯一，规则 `EQ-{类别编码}-{6位流水}`，由服务端生成，前端不可传。
  2. `qr_token` 为 UUID v4，唯一索引；支持「重新生成二维码」使旧码失效（设备搬迁/二维码破损场景）。
  3. 设备状态枚举：`IN_USE`（在用）、`IDLE`（闲置）、`REPAIRING`（维修中）、`SCRAPPED`（已报废）。
  4. 状态迁移受控：`IN_USE ⇄ IDLE` 允许；`IN_USE/IDLE → REPAIRING` 仅由工单流转触发，页面不提供手工入口；`→ SCRAPPED` 仅 ADMIN，且要求无未完结工单。
  5. 删除为逻辑删除，且**存在未完结工单（非 COMPLETED/CANCELLED）或未完成巡检任务时禁止删除**，返回具体阻塞单据号。
- **异常分支**：资产编号重复 → 409；类别/位置已停用 → 400；并发编辑 → 乐观锁冲突提示"数据已被他人修改，请刷新"。

### FR-02 二维码设备档案

- **角色**：INSPECTOR、REPAIRMAN、EQUIP_ADMIN
- **主流程**：移动端扫码 → 解析 `qr_token` → 校验登录态与数据权限 → 展示设备档案卡 → 快捷入口「开始巡检」「一键报修」
- **业务规则**
  1. 扫码接口 `GET /api/equipment/scan/{qrToken}` 只返回档案摘要，不返回采购金额等敏感字段（非 EQUIP_ADMIN 角色）。
  2. 扫码页展示：设备名称、资产编号、位置全路径、状态、健康分、最近巡检时间、最近 3 条工单。
  3. 「开始巡检」仅当该设备存在本人待执行任务时可用，否则置灰并提示原因。
  4. 二维码内容为 `{baseUrl}/#/scan?t={qr_token}`，不携带任何业务主键，防止遍历。
- **异常分支**：token 不存在或已轮换 → 提示"二维码已失效，请联系设备管理员"。

### FR-03 巡检模板管理

- **角色**：EQUIP_ADMIN
- **主流程**：新建模板（草稿）→ 维护巡检项 → 发布 → 关联计划使用
- **业务规则**
  1. 模板状态机：`DRAFT → PUBLISHED → DISABLED`。`PUBLISHED` 状态**禁止编辑任何字段与巡检项**，修改须「新建版本」，新版本 `version + 1`，旧版本自动置 `DISABLED` 但历史任务仍引用旧版本（保证历史数据可解释）。
  2. 巡检项类型与校验：
     | 类型 | 存储 | 校验规则 |
     |---|---|---|
     | `NUMBER` | decimal(12,3) | 必须落在 `[min_value, max_value]`，超出自动判为异常 |
     | `BOOL` | 0/1 | 正常值由 `normal_value` 指定（如"运行=1"） |
     | `ENUM` | 字符串 | 值必须属于 `enum_options` |
     | `TEXT` | 文本 | 长度 ≤ 500 |
  3. 每个巡检项必须配置 `abnormal_level`（LOW/MEDIUM/HIGH/CRITICAL）与 `auto_work_order`（是否自动转工单），二者共同决定 FR-06 的转单行为。
  4. 模板至少 1 个巡检项才能发布；发布时校验 `seq_no` 无重复。
  5. 被 `ENABLED` 计划引用的模板禁止删除。
- **异常分支**：编辑已发布模板 → 423 锁定；删除被引用模板 → 409 并返回引用计划列表。

### FR-04 巡检计划管理

- **角色**：EQUIP_ADMIN
- **主流程**：选择模板 → 设定作用域（设备/类别/位置）→ 设定周期 → 设定执行人策略 → 启用
- **业务规则**
  1. 作用域三种：`EQUIPMENT`（指定设备，多选）、`CATEGORY`（按设备类别）、`LOCATION`（按位置子树）。启用时**快照展开**为设备清单，后续设备新增不会自动纳入，需「重新展开」按钮显式刷新，避免任务量静默膨胀。
  2. 周期：`DAILY`（每天）、`WEEKLY`（指定周几）、`MONTHLY`（指定几号），统一由 `cycle_config` JSON 描述，如 `{"weekDays":[1,3,5],"time":"09:00"}`。
  3. 执行人策略：`FIXED`（固定人员列表轮转）、`DEPT_OWNER`（设备责任人）、`ROUND_ROBIN`（按设备顺序在人员列表中轮询）。
  4. 启用后由定时任务计算 `next_generate_time`，提前 `generate_ahead_hours`（默认 24h）生成任务。
  5. 计划停用或修改，**只影响尚未生成的任务**，已生成任务不回滚。
- **异常分支**：作用域展开结果为空 → 保存成功但状态保持 `DISABLED` 并提示"当前作用域下无可用设备"；周期配置非法 → 400。

### FR-05 巡检任务管理

- **角色**：INSPECTOR（执行）、EQUIP_ADMIN（监督）
- **主流程**：任务生成 → 待执行列表 → 扫码开始 → 逐项填写（可存草稿）→ 提交 → 生成记录与异常
- **业务规则**
  1. 任务状态机：`PENDING → IN_PROGRESS → SUBMITTED → COMPLETED`，另有 `OVERDUE`（系统置位，可从 PENDING/IN_PROGRESS 进入，仍可继续执行）、`CANCELLED`（管理员取消，需理由）。
  2. 唯一约束 `(plan_id, equipment_id, plan_date)`，防止定时任务重复执行产生重复任务。
  3. 开始执行时若 `now > sla_due_time`，任务 `overdue_flag = 1`，仍允许执行但计入逾期统计，不阻断业务。
  4. 提交前置校验：所有 `required = 1` 的项必须有值；`NUMBER` 项在范围内；任一 `is_abnormal = 1` 的项必须填异常描述且至少 1 张照片。
  5. 提交时服务端二次复算异常：即使前端未标记，数值越界 / BOOL 非正常值 / ENUM 非正常值 一律置 `is_abnormal = 1`，前端标记不作为唯一依据。
  6. 草稿仅保存到 Redis（key `inspect:draft:{taskId}:{userId}`，TTL 24h），提交时才落库，避免半成品污染业务表。
  7. 任务详情展示**同设备同巡检项最近 3 次历史值**，便于判断劣化趋势。
- **异常分支**：非 assignee 提交 → 403；任务已 COMPLETED 再次提交 → 409；设备在此期间报废 → 提交失败并提示联系管理员。

### FR-06 巡检异常上报（异常自动转维修工单，核心）

- **角色**：INSPECTOR 上报；EQUIP_ADMIN 处置
- **主流程**：任务提交时异常项自动生成 `insp_anomaly` → 判定是否转单 → 满足条件自动创建工单 → 通知派单角色
- **业务规则（转单判定，必须逐条实现）**
  1. **直接转单**：`item.is_abnormal = 1` 且 `(template_item.auto_work_order = 1 或 anomaly.level ∈ {HIGH, CRITICAL})`。
  2. **累计升级**：同一设备同一巡检项 **24 小时内异常次数 ≥ 2**，本次异常等级自动提升为 `HIGH` 并转单（即便 `auto_work_order = 0`）。
  3. **不转单**：`level = LOW` 且 `auto_work_order = 0`，仅登记异常，进入异常池由管理员人工决定转单或关闭。
  4. **合并规则（防工单风暴）**：若该设备已存在状态非 `COMPLETED/CANCELLED` 的工单，且 `fault_type` 相同，则**不新建工单**，而是把新异常挂到已有工单下，追加异常说明并给维修人发消息。合并动作写入 `wo_status_log`（action = `MERGE_ANOMALY`），不改变工单状态。
  5. **等级映射**：`CRITICAL → P1`、`HIGH → P2`、`MEDIUM → P3`、`LOW → P4`。
  6. **工单初始状态**：一律 `PENDING_DISPATCH`，派单人由 `sla_policy.escalate_role_code` 对应角色认领，系统不做自动派单（保留人工决策，避免"自动派给休假人员"）。
  7. **事务边界**：任务提交 + 巡检项落库 + 异常落库 + 工单创建 + 状态日志 + 消息，同一 `@Transactional` 本地事务；任一步失败整体回滚，任务保持 `IN_PROGRESS` 可重试。
  8. **幂等**：`wo_work_order.anomaly_id` 建唯一索引，重复提交/重试不会产生第二张工单。
  9. **设备联动**：工单创建成功后设备状态置 `REPAIRING`；工单 `COMPLETED` 后置回 `IN_USE`；工单 `CANCELLED` 后置回创建前状态（记录在工单 `prev_equipment_status`）。
- **异常分支**：转单后通知失败 → 不回滚业务，消息表落 `FAILED` 并由补偿任务重试（保证"业务优先，通知可补"）。

### FR-07 维修工单管理

- **角色**：EQUIP_ADMIN 创建/取消；全角色按权限查看
- **主流程**：手工报修（扫码或台账发起）→ 工单 `PENDING_DISPATCH` → 进入派单池
- **业务规则**
  1. 工单编号 `WO{yyyyMMdd}{5位流水}`，Redis 原子自增生成，唯一索引兜底。
  2. 必填：设备、故障类型（字典）、故障描述（≥10 字）、紧急等级（P1–P4）、期望完成时间（可空，为空按 SLA 政策推算）。
  3. 工单详情聚合：基础信息、状态时间轴（`wo_status_log`）、维修记录、备件明细、附件、SLA 剩余时间、关联异常列表。
  4. 取消：仅 `PENDING_DISPATCH`、`PENDING_ACCEPT` 可取消，必须填原因，取消后释放设备状态。
  5. **禁止任何接口直接 set status**，全部经状态机（详见文档 02 第 5 节）。
- **异常分支**：同设备存在未完结工单时手工报修 → 返回 409 并提示已存在工单号，可选择「追加到已有工单」。

### FR-08 工单派发与接单

- **角色**：EQUIP_ADMIN 派单；REPAIRMAN 接单
- **主流程**：派单池 → 选择维修人（展示技能标签与在手工单数）→ 派单 → 维修人接单 → 进入维修中
- **业务规则**
  1. 派单人必须是 `EQUIP_ADMIN` 或 `ADMIN`，且不能把自己派给自己不存在的技能（不校验技能匹配为硬约束，仅作提示）。
  2. 派单记录写 `wo_dispatch_log`（dispatch_type = `ASSIGN`），并写 `wo_status_log`（`PENDING_DISPATCH → PENDING_ACCEPT`）。
  3. 接单仅限 `assignee_id` 本人；接单写 `accept_time`，若 `accept_time > response_due_time` 则该工单标记响应超时。
  4. **拒接**：`PENDING_ACCEPT → PENDING_DISPATCH`，必须填拒接原因，通知派单人；同一工单 `reject_count ≥ 3` 时升级通知 MANAGER。
  5. **转派**：`PENDING_ACCEPT`（未接单）可由派单人直接转派；`IN_PROGRESS`（已接单）转派需 ADMIN 操作并填原因，原维修人已记录的工时保留在 `wo_repair_record` 中不删除。
  6. **撤回**：`PENDING_ACCEPT → PENDING_DISPATCH`，派单人在维修人接单前可撤回。
  7. 并发保护：接单使用条件更新 `WHERE id = ? AND status = 'PENDING_ACCEPT' AND assignee_id = ?`，影响行数为 0 即抛"工单状态已变更"。
- **异常分支**：维修人被禁用 → 派单接口 400；同一维修人在手工单超阈值（默认 10）→ 派单仍允许，但返回警告标记由前端提示。

### FR-09 维修过程记录

- **角色**：REPAIRMAN（本人工单）
- **主流程**：接单后追加维修记录（诊断/处理/完工）→ 上传照片 → 记录耗时 → 提交验收
- **业务规则**
  1. 记录类型：`DIAGNOSIS`（故障诊断）、`PROCESS`（处理过程）、`FINISH`（完工说明）、`OTHER`。
  2. 每条记录可附 0–5 张图片（jpg/png，单张 ≤ 10MB），图片元数据落 `sys_file`。
  3. **提交验收前置校验（缺一不可）**：至少 1 条 `FINISH` 类型记录；至少 1 张完工照片；已申请备件全部处于 `ISSUED` 或 `REJECTED`（无 `APPLIED` 悬挂）；填写 `repair_summary`。
  4. 挂起：等待备件或外协时可 `IN_PROGRESS → SUSPENDED`，必须填挂起原因；挂起期间 SLA 计时暂停（累计 `suspend_total_minutes`），恢复时顺延 `resolve_due_time`。
  5. 维修记录一旦提交不可删除，只能追加更正记录（`record_type = OTHER`，内容前缀"更正："），保证审计完整性。
- **异常分支**：非本人操作 → 403；工单不在 `IN_PROGRESS/SUSPENDED` → 409。

### FR-10 维修验收

- **角色**：VERIFIER（或 EQUIP_ADMIN）
- **主流程**：待验收列表 → 查看维修记录与备件 → 现场确认 → 通过 / 驳回
- **业务规则**
  1. **禁止自验收**：`verify_user_id != assignee_id`，后端硬校验。
  2. 通过：`PENDING_VERIFY → COMPLETED`，写 `actual_finish_time`、`close_time`；设备状态回 `IN_USE`；触发该设备健康分重算（异步，页面刷新可见）；SLA 结算（`overdue_flag` 定档）；通知报修人与派单人。
  3. 驳回：`PENDING_VERIFY → IN_PROGRESS`，`reject_count + 1`，驳回原因必填（≥10 字），工单回到原维修人待办；**SLA 不重置**，超时继续累计（防止通过反复驳回规避考核）。
  4. 质量评分 1–5 分必填，进入维修人员绩效统计。
  5. 备件退料：驳回时若备件未实际使用，维修人可发起退料（`RETURN` 流水，库存回增），退料后才可再次提交验收。
- **异常分支**：验收人 = 维修人 → 403 `WO_SELF_VERIFY_FORBIDDEN`；工单不在 `PENDING_VERIFY` → 409；同一工单并发验收 → 条件更新保证只有一次生效。

### FR-11 备品备件管理

- **角色**：EQUIP_ADMIN
- **主流程**：备件建档 → 设置安全库存 → 库存预警 → 停用/启用
- **业务规则**
  1. 备件编码 `SP-{6位}` 唯一；`current_stock` 不得为负（DB 层 `CHECK (current_stock >= 0)` + 应用层条件更新双保险）。
  2. 安全库存预警：`current_stock <= safety_stock` 时进入预警清单，仪表盘展示数量，消息推送给 EQUIP_ADMIN（每日 08:00 汇总推送一次，避免刷屏）。
  3. 停用备件不可被工单申请，已申请的允许继续出库。
  4. `current_stock` 只能通过库存流水变更，**禁止提供直接修改库存的接口**（盘点通过 `ADJUST` 流水实现并记录原因）。
- **异常分支**：删除有流水的备件 → 409，只能停用。

### FR-12 库存出入库

- **角色**：EQUIP_ADMIN（仓管）
- **主流程**：工单申请备件 → 审批出库 → 扣减库存 → 写流水；采购入库 / 退料入库同理
- **业务规则**
  1. 流水类型：`IN`（入库）、`OUT`（出库）、`RETURN`（退料）、`ADJUST`（盘点调整，可正可负）。
  2. 每条流水记录 `before_stock`、`after_stock` 快照，保证任意时点可反推。
  3. 出库扣减使用原子 SQL：`UPDATE sp_part SET current_stock = current_stock - #{qty} WHERE id = #{id} AND current_stock >= #{qty}`，影响行数 0 即库存不足，抛业务异常回滚。
  4. 工单备件申请（`APPLIED`）**不锁库存**，出库时才扣减；为避免超卖，出库失败时提示当前可用量并允许修改数量重新申请。
  5. 流水不可修改、不可删除，只能反向冲正（生成对应 `IN`/`RETURN` 流水并注明冲正原单号）。
- **异常分支**：并发出库导致库存不足 → 友好提示"库存不足，当前可用 X"；备件已停用 → 400。

### FR-13 SLA 超时预警

- **角色**：EQUIP_ADMIN 配置；MANAGER 查看达成率
- **主流程**：配置 SLA 政策（按等级）→ 工单创建时计算响应/修复时限 → 定时扫描 → 预警与升级
- **业务规则**
  1. `sla_policy` 按 `level`（P1–P4）定义 `response_minutes`（响应时限）与 `resolve_minutes`（修复时限），默认：P1 30/240、P2 60/480、P3 240/1440、P4 480/2880（分钟）。
  2. 工单创建时固化 `response_due_time`、`resolve_due_time`，**后续改政策不影响在途工单**（避免追溯性篡改考核结果）。
  3. 定时任务每分钟扫描（单实例 `@Scheduled` + 数据库锁表防重）：
     - 剩余时间 ≤ `warn_percent`（默认 80%）→ `sla_status = WARN`，发预警消息；
     - 已超时 → `sla_status = OVERDUE`，`overdue_flag = 1`，发消息给维修人 + 派单人 + MANAGER；
     - **超时只升级告警，不自动改工单状态**，业务状态与考核状态解耦。
  4. 挂起（`SUSPENDED`）期间暂停计时，恢复时 `resolve_due_time += suspend_duration`。
  5. SLA 达成率 = 未超时完结工单数 / 已完结工单数，按角色、按等级、按月份三个维度出数。
- **异常分支**：政策被删除但仍有在途工单 → 禁止删除，只能停用。

### FR-14 设备健康评分

- **角色**：系统计算；全角色查看
- **主流程**：每日 02:00 全量重算 → 写 `eq_health_snapshot` → 更新设备主表 `health_score`
- **业务规则（公式必须可实现、可解释）**

  ```
  基础分 100，统计窗口：近 90 天
  故障扣分 F = min(50, Σ 工单权重)，权重 P1=15、P2=8、P3=4、P4=1
  超时扣分 T = min(20, 超时工单数 × 3)
  异常扣分 A = min(20, 巡检异常数 × 2)
  逾期扣分 M = min(10, 逾期巡检任务数 × 1)
  正常巡检加分 R = min(10, 正常任务数 × 0.2)
  健康分 = clamp(100 - F - T - A - M + R, 0, 100)
  ```

  1. 分级：`≥90 健康`、`75–89 亚健康`、`60–74 预警`、`<60 高危`。
  2. 每次工单完结、任务提交后触发**单设备增量重算**（异步），保证页面实时性；每日 02:00 做全量兜底重算。
  3. 快照表按天唯一，支持 30/90 天趋势折线。
- **异常分支**：设备无任何历史数据 → 初始分 100，等级"健康"（新设备不应被误判为高危）。

### FR-15 运维数据分析

- **角色**：MANAGER、EQUIP_ADMIN、ADMIN
- **业务规则**
  1. 所有统计**必须由 SQL 聚合实时计算或按日快照汇总**，禁止在前端或后端硬编码任何数值、禁止返回 mock。
  2. 仪表盘指标：今日应巡检/已完成/完成率、待派单数、在修工单数、待验收数、超时工单数、本月 MTTR（平均修复时长）、本月备件成本、健康分布（4 档计数）、SLA 达成率。
  3. 图表：近 30 天工单趋势（新建/完结双折线）、巡检完成率趋势、故障类型 Top10（柱状）、维修人员工作量（按完结工单数与平均耗时）、备件消耗 Top10、健康分分布（环形）。
  4. 查询默认按当前用户数据权限过滤；MANAGER 看全量。
  5. 空数据必须返回空数组并由前端渲染空状态，不得返回伪造示例数据。
- **异常分支**：时间跨度 > 365 天 → 400，限制查询成本。

### FR-16 用户、角色与权限管理

- **角色**：ADMIN
- **业务规则**
  1. 用户：用户名唯一、密码 BCrypt（强度 10）、手机号唯一；禁用用户即时失效（Redis 会话黑名单 + 每次请求校验用户状态）。
  2. 角色：`role_code` 唯一，一个用户可多角色，权限取并集。
  3. 权限：树形（菜单/按钮/接口），权限码格式 `{模块}:{资源}:{动作}`，如 `wo:workorder:dispatch`。
  4. 数据范围：`ALL` 全量、`DEPT` 本部门及下级、`SELF` 仅本人，由 MyBatis-Plus 拦截器统一注入 SQL 条件。
  5. 修改角色权限后，已登录用户的权限缓存立即失效（删 Redis key `perm:user:{id}`），下一次请求重新加载。
  6. 内置 `ADMIN` 角色不可删除、不可修改权限集合，防止把自己锁死。
- **异常分支**：删除仍被用户引用的角色 → 409；ADMIN 禁用自己 → 403。

### FR-17 系统消息与操作审计

- **角色**：全员（消息）、ADMIN（审计）
- **业务规则**
  1. 消息类型：`TASK`（新任务/任务即将逾期）、`WORKORDER`（派单/接单/驳回/验收）、`SLA`（预警/超时）、`SYSTEM`（公告）。
  2. 消息带 `biz_type + biz_id`，点击跳转对应业务详情页；未读数前端 60 秒轮询（`/api/system/messages/unread-count`，Redis 计数），不做 WebSocket（单机演示场景收益低）。
  3. 审计日志通过 AOP 注解 `@AuditLog(module, action)` 采集：操作人、模块、动作、URI、脱敏后的请求参数（密码/手机号中间四位打码）、结果、错误信息、IP、耗时。
  4. 审计日志异步写入（线程池 + 队列，队列满则降级同步），不可修改删除，保留 180 天后由定时任务归档删除。
  5. 登录成功/失败均记录，连续 5 次失败锁定账号 10 分钟（Redis 计数）。

## 6. 术语表

| 术语 | 定义 |
|---|---|
| 巡检模板 | 一组巡检项的定义，是"查什么、怎么判合格"的标准 |
| 巡检计划 | 模板 + 作用域 + 周期的调度规则，负责生成任务 |
| 巡检任务 | 某台设备在某天要执行的一次巡检，是执行与考核的最小单位 |
| 异常 | 巡检项不合格产生的记录，是工单的上游来源 |
| 工单 | 一次维修请求的完整生命周期载体 |
| 挂起 | 因缺备件/等外协暂停维修，SLA 计时冻结 |
| MTTR | 平均修复时长 = Σ(actual_finish_time - accept_time) / 完结工单数 |
| SLA 达成 | 在 `resolve_due_time` 之前完结的工单占比 |
